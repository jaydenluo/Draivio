# Image Pro 模型选择器设计

## 目标

让用户在选择 Image Pro 时，先理解请求将从哪个“服务来源”发出，再选择该来源支持的具体模型；同时清楚知道使用的是 Draivio 登录积分、自己的供应商余额，还是某个平台的自定义接口。

## 采用的交互

采用“服务来源 → 模型”的两级选择器。

默认收起时展示一行摘要：

```text
服务来源：OpenAI · 自定义密钥
模型：gpt-image-2.5
```

点击“服务来源”后展开可选连接：

- `Draivio 云端`：使用用户在 Draivio 的登录积分；模型可显示为 `Image Pro`。
- `OpenAI`：使用用户自己的 OpenAI API Key；费用由 OpenAI 账户承担。
- `火山引擎`：使用用户在火山引擎配置的密钥或端点；协议可标记为 `OpenAI 兼容`。
- 其他平台：沿用相同结构，不需要新增特殊命名规则。

选择服务来源后，模型列表只展示该来源实际支持的模型。模型名称保持供应商返回的原名，例如 `gpt-image-2.5`；产品内部可另外保存稳定的模型 code，不把协议名拼进模型标题。

## 命名规则

### 用户界面

使用“服务来源”作为一级概念。来源摘要格式为：

```text
{平台名称} · {认证/额度方式}
```

示例：

- `Draivio 云端 · 使用登录积分`
- `OpenAI · 自定义密钥`
- `火山引擎 · 自定义密钥`
- `火山引擎 · OpenAI 兼容`

“OpenAI 兼容”只表示请求协议，不表示实际服务商。避免使用 `OpenAI(火山)` 这种会把协议和供应商混为一谈的写法。

### 内部数据

服务来源由以下字段构成：

- `provider`: 实际计费或提供服务的平台，例如 `draivio`、`openai`、`volcengine`。
- `credentialMode`: `managed_credits`、`user_api_key` 或其他认证类型。
- `endpoint`: 实际请求地址或端点配置。
- `protocol`: `native`、`openai_compatible` 等协议类型。
- `model`: 服务来源下可用的模型 code、展示名和能力约束。

内部数据可以把同一平台配置成多个服务来源，例如多个 OpenAI API Key；用户界面通过不同的来源摘要区分它们。

## 费用和状态展示

- Draivio 云端显示“预计消耗：12 积分”以及当前积分余额入口。
- 自定义供应商显示“费用由 OpenAI/火山引擎账户承担”，不伪造 Draivio 积分价格。
- 无法读取余额时显示“余额由供应商管理”，并保留请求前的可用性检查。
- 来源或模型不可用时，在对应列表项上显示原因，并禁止提交；已选来源失效时不自动切换到另一个来源。

## 数据流

1. 加载服务来源列表。
2. 用户选中服务来源。
3. 根据来源加载模型、能力和限制。
4. 用户选择模型并查看费用/额度说明。
5. 提交请求时同时发送 `sourceId` 和 `modelCode`。
6. 操作历史保存来源、模型、协议、费用来源和请求状态，便于重试与追溯。

## 验收标准

- 用户无需阅读协议名，也能区分 Draivio 积分、自己的 OpenAI Key 和火山引擎 Key。
- 同名模型来自不同服务来源时，选择器仍能明确区分。
- 火山引擎的 OpenAI 兼容接口不会显示为 `OpenAI(火山)`。
- 模型列表只展示当前服务来源可用的模型。
- 主界面默认保持两行以内的信息密度，详细信息通过展开查看。
