# Raster preview performance

`processRaster` now uses a dedicated module Worker where available. Caller-owned source buffers are cloned (never detached); output uses transfer, and completion/error/cancellation terminates the worker. A supported cooperative fallback performs real pixel ranges between event-loop yields and adapts toward 8ms of compute per range. It shares the exact compositor with full-resolution rendering. The common opaque-normal path copies bytes without allocating RGB arrays per pixel; masked/transparent/other blend modes keep the W3C straight-alpha formula.

The default budget rejects above 16,777,216 pixels or 256MiB of accounted input/output/worker-clone buffers before output allocation/worker dispatch. 8192² therefore reports a clear shrink/tile limit rather than attempting to allocate a full-frame output. Explicit budgets remain available to callers.

`RasterSurface.compositeAsync` atomically publishes only the current surface revision and clears intermediate output. `RasterPreviewQueue` caps preview size at 2048, nearest-neighbor downsamples (preview only), debounces changes, cancels prior work, and holds a single explicitly revision-keyed result. Include document ID, content revision and every compositing parameter in the key. Results are borrowed until next run/dispose; encoded document sources/undo history remain separate. Dispose the queue on close/document change. This is a raster backend API; the existing SVG document renderer/export still keeps its own full-resolution path and is not silently downsampled.

Run `node scripts/benchmark-raster.mjs` for reproducible reference measurements. It retains all 5 cold-process runs and 20 warm runs after 3 warmups. Input is a decoded 2048² RGBA image with one opaque normal layer (same input as the original failed baseline); output allocation/composition/yields are timed, source construction/decoding is recorded as excluded. This measures the local compositor, not network/model latency or whole-app GPU rendering. The dedicated-worker test separately records startup, source clone, transfer, worker compute and main dispatch time across 7 fresh workers using actual OS threads and the production bundled Worker module.

`docs/evidence/performance/benchmark.json` records CPU/OS/runtime, p50/p95, max synchronous compute slice, input/output buffer high-water accounting, sampled real process RSS and cancellation latency. Worker source clones are included in buffer accounting. RSS includes Node/runtime overhead and is sampled, not an exact browser GPU peak. `adoption-lifecycle.json` records 20 actual local PNG results adopted through the production reducer and undone; owned pixel buffers are zeroed and evicted each time. PNG sources intentionally retained by results/history are separately reported. Clearing owned buffers is not represented as immediate garbage collection of all JS or GPU memory.

Cycle 2 repair adds an inner compositor deadline check every 2048 pixels and a 262,144-pixel outer range cap. A slice that reaches its 8ms budget returns the exact next pixel; the scheduler yields and resumes there, preserving masks/blends and all source pixels. Unlike throughput feedback alone, a cold or newly expensive range can now stop before its original row block ends. Synchronous full-resolution callers omit the deadline. These cooperative checks do not prevent an operating-system pause or GC between checks; measured wall-time failures remain failures and are retained. The previous exclusive 68.904ms outlier had no phase trace and its precise cause is unknown. A separate temporary 23-run phase diagnostic recorded initialization and real range wall/CPU timings (max 6.292ms) without reproducing that outlier; that diagnostic is not acceptance evidence for the repair.
